# Google Knowledge Catalog vs. ok-skills extraction

Google Cloud Knowledge Catalog and the extraction skills in this repository solve the same core problem from opposite ends of the stack. Both turn scattered evidence into structured context so downstream agents stop producing plausible-looking answers that violate actual rules.

Knowledge Catalog is a managed Google Cloud service, formerly Dataplex Universal Catalog, built around BigQuery and Lakehouse data assets. The skills in this repository, [extract-meeting-notes](../../extract-meeting-notes/SKILL.md) and [extract-session-details](../../extract-session-details/SKILL.md), build a plain Markdown knowledge store in Git for coding, SRE, and assistant agents reading meetings, transcripts, and project documents.

This comparison maps Knowledge Catalog's concepts directly onto the files in this repository so collaborators can check whether the extraction design captures everything that matters, where it is already stronger than Google's model, and which gaps are worth closing. Facts about Knowledge Catalog reflect Google Cloud documentation and the `GoogleCloudPlatform/knowledge-catalog` sample repository as inspected on November 16, 2026. Knowledge Studio enrichment tasks, context sets, and batch governance workflows were in Preview at that date, and this essay is a documentation-based architectural comparison rather than a measured benchmark.

## 1. How Google Knowledge Catalog works

A database schema can tell an agent column names and types, yet still leave business rules unstated. An analytics agent querying `orders`, `order_items`, and `refunds` can write valid SQL that executes without errors and still return the wrong revenue number if it misses that a discount column is per line rather than per unit, canceled orders do not count, refunds follow an explicit cutoff date, or items and refunds must each be aggregated to order grain before joining.

Knowledge Catalog addresses that gap across six parts:

- **Raw inventory separate from domain overlays.** The catalog indexes physical tables and technical metadata automatically for BigQuery without copying table rows. Managed enrichment does not overwrite underlying BigQuery table descriptions or source policy files. Instead, it writes generated overlay documents inside a bounded **context set** using the `table-context`, `concept`, `knowledge-base`, and `learning` document roles, linked to the physical tables by a `reference` link. See [Knowledge Catalog overview](https://docs.cloud.google.com/knowledge-catalog/docs/introduction), [About metadata](https://docs.cloud.google.com/knowledge-catalog/docs/metadata-overview), and [Context sets overview](https://docs.cloud.google.com/knowledge-catalog/docs/context-sets).
- **Rules paired with field traps and worked examples.** Knowledge Catalog treats schemas, business concepts, field-level notes, and verified **Query Templates** as complementary layers. A concept defines a metric, a table overlay warns about field units and join grain, and a Query Template pairs a natural-language question with validated SQL. Enrichment preserves certified Query Templates without overwriting or deleting them. See [About data context](https://docs.cloud.google.com/knowledge-catalog/docs/about-context) and [Context sets overview](https://docs.cloud.google.com/knowledge-catalog/docs/context-sets).
- **Typed relationships.** Entry links distinguish `reference`, `schema-join`, `definition`, `synonym`, and `related`, separate from data lineage. A reference link says a context document describes a table; it does not assert that joining raw rows across two tables is safe. See [About metadata](https://docs.cloud.google.com/knowledge-catalog/docs/metadata-overview) and [Knowledge Studio overview](https://docs.cloud.google.com/knowledge-catalog/docs/knowledge-studio).
- **Four-phase managed enrichment with benchmark gates.** An enrichment task reads target assets plus read-only knowledge signals such as Cloud Storage documents, glossaries, GitHub files, Google Workspace, Confluence, Jira, and BigQuery query history. It analyzes evidence, drafts structured context, runs deterministic validity checks and confidence scoring, and optionally tests the draft against an evaluation set of questions paired with reference SQL, kept separate from a curation set of seed questions. Proposals stage as change requests. Default auto-publish gates require run confidence of at least 0.85, zero invalid proposals, and no more than a 5 percentage-point drop in benchmark accuracy. Deletions always require manual review. See [About enrichment tasks](https://docs.cloud.google.com/knowledge-catalog/docs/about-enrichment-tasks), [Create enrichment tasks](https://docs.cloud.google.com/knowledge-catalog/docs/create-enrichment-tasks), and [Configure prerequisites for enrichment tasks](https://docs.cloud.google.com/knowledge-catalog/docs/configure-enrichment-prerequisites).
- **Self-learning from live agent traces.** Once context is live, enrichment can mine Gemini Enterprise conversation traces and BigQuery agent analytics tables for recurring ambiguities or clarification gaps, proposing `learning` documents for human review. Google states that customer schemas, signals, and traces are not used to train its foundation models. See [Evaluate and approve enrichment proposals](https://docs.cloud.google.com/knowledge-catalog/docs/manage-enrichment-runs) and [About enrichment tasks](https://docs.cloud.google.com/knowledge-catalog/docs/about-enrichment-tasks).
- **Custom agent path and scoped runtime retrieval.** Alongside console-managed tasks, Google publishes a Python ADK sample in [samples/enrichment](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/samples/enrichment/README.md) and [Build an agent to enrich your metadata](https://docs.cloud.google.com/knowledge-catalog/docs/build-agent-to-enrich-metadata) that downloads table metadata to Markdown, runs an agent with local document tools to write revised Markdown, relies on `git diff` for human review, and publishes approved Overview aspects. At runtime, consuming agents call the MCP tools `search_entries`, `lookup_entry`, and `lookup_context` or the regional `:lookupContext` REST endpoint with a soft character budget, reading a root index and verified examples before drilling into deep documents. Reading metadata never grants permission to query underlying data. See [Retrieve context for data assets](https://docs.cloud.google.com/knowledge-catalog/docs/retrieve-data-context) and [Knowledge Catalog MCP reference](https://docs.cloud.google.com/knowledge-catalog/docs/reference/mcp).

## 2. What ok-skills currently implements

The extraction kit in this repository keeps all state in plain Markdown files inside the target project's Git repository, with no database, cloud service, or retrieval runtime required:

- **Two source-specific entry skills.** [extract-meeting-notes](../../extract-meeting-notes/SKILL.md) targets design discussions, standups, sprint planning, process walkthroughs, and incident reviews. It preserves attributed definitions and scope boundaries with the records they qualify, plus rule applications confirmed by the person responsible for the rule. [extract-session-details](../../extract-session-details/SKILL.md) targets human-agent session transcripts, AI chat exports, tool traces, and attached documents across seven categories: project knowledge, decisions and constraints, successful strategies, failures and recoveries, user steering, agent behavior patterns, and unresolved state. It keeps user corrections and observed usage that fix workflow terms, labels inferred meanings explicitly, links demonstrated rule applications with their evidence limits, distinguishes hook-captured views of older sessions from new independent events, and extracts structured four-part research or method claims with `Claim`, `Support`, `Applies when`, and `Limits`.
- **Three-stage shared store.** Both skills write the same store specified in [store.md](../../extract-session-details/references/store.md) and [knowledge.md](../../extract-session-details/references/knowledge.md). Stage 1 compresses each distinct source alone under `compressed/` with exact line links, verbatim user prompts, workflow-specific definitions, and linked rule applications. Stage 2 builds one evidence document per source under `docs/extractions/`, deduplicating shared passages with hold-once rules and bidirectional typed relations: `Revises`, `Supersedes`, `Adapted from`, `Another export of`, `Continues`, `Conflicts with`, `Quotes`, `Produced in`, and `Judged in`. Stage 3 routes actionable records in event-date order onto canonical subject pages under `docs/knowledge/` for `project`, `service`, `feature`, `procedure`, `decision`, and `problem` types. Exact-name subject matching and item-level updates both check scope compatibility before merging or resolving an existing item. The store is tracked by the subject registry at `docs/knowledge/subjects.md`, the source ledger at `docs/knowledge/sources.md`, and the holding page at `docs/knowledge/unassigned.md`.
- **Deterministic structural checking.** [check_store.py](../../extract-session-details/scripts/check_store.py) verifies every relative link and `#L` line anchor bound, rejects unexpanded template tokens, checks the closed status vocabulary on subject pages, enforces index descriptions against page front matter, verifies bidirectional agreement across pages, registry, ledger, and holding page, and can export the store to JSON Lines.
- **Adjacent skills in the repository.** [agent-context-strategy.md](agent-context-strategy.md) records the content recommendation and tool verdicts behind this extraction-only scope. [project-memory-investigation-prompt](../../project-memory-investigation-prompt/SKILL.md) scopes cross-session project memory research before running extraction. [session-forks](../../session-forks/SKILL.md) tracks conversational branches and continuation handoffs in `forks/` when an agent needs thread-level recovery rather than a full knowledge store.

## 3. Side-by-side comparison

| Dimension | Google Knowledge Catalog | ok-skills extraction | Assessment |
|---|---|---|---|
| **Primary unit of context** | BigQuery and Lakehouse tables plus domain concepts, table overlays, and SQL templates in a context set | Six subject page types, `project`, `service`, `feature`, `procedure`, `decision`, and `problem`, plus per-source evidence documents | Equivalent overlay pattern, adapted from analytics tables to software and operations work |
| **Raw sources vs. derived context** | Underlying tables and read-only knowledge signals stay untouched; enrichment writes context-set overlays | Raw transcripts and notes stay untouched; Stage 2 evidence and Stage 3 subject pages sit on top with `#L` line links | Covered in ok-skills |
| **Extraction rules: what to capture vs. skip** | Fixes output containers and blocks overwriting raw descriptions or certified templates; relies on undisclosed internal prompts plus a free-text Goal box | Explicit source-specific rules for meetings and sessions, closed status vocabulary, verbatim user quotes, hold-once deduplication, captured-view guards, and research-claim structure | ok-skills is much stronger and more transparent |
| **Authority and conflict resolution** | No documented built-in source-precedence rule when signals disagree; governance uses last-writer-wins | Strict separation of proposal vs. decision, assignment vs. acceptance, submission vs. approval, observation vs. claim, and first-hand vs. second-hand; conflicts stay visible with attribution | ok-skills is stricter and safer against silent overwrites |
| **Learning from live agent sessions** | Self-learning mines Gemini Enterprise and BigQuery agent traces into candidate `learning` documents | `extract-session-details` extracts user steering, failures, recoveries, and recurring `problem` pages with inferred lessons tagged `candidate` | Covered in ok-skills, with clearer authority separation between user corrections and agent traces |
| **Local term definitions, scope, and worked examples** | Pairs metric concepts with field-level traps on table overlays and certified question-to-SQL Query Templates | Keeps workflow-specific definitions with the records they qualify, checks scope compatibility at both subject matching and item updates, and links rules to sourced applications with proof limits while keeping purely illustrative examples in evidence | Core distinction is now covered in the instructions, though not yet proven with a public held-out test run in this repo |
| **Protecting curated edits across re-runs** | Certified Query Templates are preserved without modification or deletion across enrichment runs; other manual edits carry no such promise | Subject rebuilds carry over `owner instruction` history rows, and re-extraction keeps holders and relations, but no general lock protects manually curated notes or examples | Minor gap worth deciding if re-runs become frequent |
| **Review gate, versioning, and rollback** | Managed console change requests with Edit, Approve, Deny, and manual Deletions, or `git diff` in the custom ADK sample; no documented general rollback | Uncommitted edits reviewed via `git diff` and approved by `git commit`, backed by full Git history and rollback | Git commit is simpler and stronger on history, provided extraction agents do not auto-commit unreviewed Stage 3 updates |
| **Downstream quality evaluation** | Optional evaluation set separate from curation seed questions; Gemini SQL-equivalence autorater measures whether candidate context improves or regresses answers | `check_store.py` checks links, anchors, schema, and registry/ledger consistency; no task-level benchmark in this repo tests whether a consuming agent answers better with the store | Biggest real gap in ok-skills |
| **Domain scoping and progressive disclosure** | Bounded context sets per domain; consumers read a root index and verified examples before drilling into table context or concepts | `docs/knowledge/index.md`, `subjects.md`, and one canonical home per procedure or decision prevent duplication; no per-domain packaging or context-budget layer | Partial fit; sufficient for small to medium stores, intentionally deferred for retrieval |
| **Runtime serving and access control** | MCP server and `:lookupContext` REST API with soft character budget and IAM filtering; metadata read access stays separate from data execution permission | No serving API or runtime enforcement; agents read Markdown files directly; `knowledge.md` notes that relevance does not grant access and repo permissions are the only boundary | Out of scope by design under extraction-only scope |

## 4. Where ok-skills is already stronger

Three parts of this repository go beyond what Knowledge Catalog documents:

**Explicit extraction discipline.** Knowledge Catalog constrains what container an agent writes into, not how it judges messy human communication. Google does not publish the managed enrichment agent's internal prompts, and [Create enrichment tasks](https://docs.cloud.google.com/knowledge-catalog/docs/create-enrichment-tasks) relies on the operator's natural-language Goal to describe what matters. By contrast, [extract-meeting-notes](../../extract-meeting-notes/SKILL.md) and [extract-session-details](../../extract-session-details/SKILL.md) spell out exact semantic rules: a proposal is not a decision, an assignment is not acceptance, a blanket "ok proceed" approves no single item, an observation is not a root cause, a captured read of an older transcript is not a second occurrence, and a reported paper claim stays `claimed by` or `second-hand` rather than `observed`.

**Event-date ordering and conflict preservation.** In [About governance workflows](https://docs.cloud.google.com/knowledge-catalog/docs/about-governance-workflows), Knowledge Catalog applies last-writer-wins governance and documents no general rollback command or immutable version viewer. In [knowledge.md](../../extract-session-details/references/knowledge.md), `ok-skills` applies records strictly in event-date order regardless of ingestion order, replays late-arriving evidence against later records, preserves superseded positions in a dedicated section, and keeps unresolved disagreements visible side by side rather than letting a newer assistant proposal overwrite an owner decision.

**Git as both review gate and audit trail.** Using `git diff` and `git commit` as the approval step mirrors Google's own custom ADK sample in [Build an agent to enrich your metadata](https://docs.cloud.google.com/knowledge-catalog/docs/build-agent-to-enrich-metadata), while adding full diff history, branching, and trivial rollback without maintaining a separate proposal queue or console UI. Combined with [check_store.py](../../extract-session-details/scripts/check_store.py), structural errors fail fast before commit.

## 5. Real gaps worth closing or deciding

Comparing the two systems surfaces four concrete questions rather than a reason to adopt a cloud catalog.

### 1. Testing whether extracted context helps a downstream agent

Knowledge Catalog's strongest operational idea is judging candidate context by downstream behavior rather than prose quality. Even a run with 0.91 confidence is held back if accuracy on held-out questions drops past the tolerance. It also warns against reusing the same questions for both tuning and evaluation.

In `ok-skills`, [check_store.py](../../extract-session-details/scripts/check_store.py) proves structural integrity: links resolve, line ranges exist, statuses fit the vocabulary, and the ledger matches every page. It cannot detect whether an extractor merged two unrelated meanings, dropped a material condition, or wrote pages that still mislead a coding or SRE agent. For instance, the workflow-scope and rule-application rules now written into [store.md](../../extract-session-details/references/store.md) and [knowledge.md](../../extract-session-details/references/knowledge.md) look sound on paper, yet this repository does not bundle an executable held-out fixture suite or downstream consumer check proving an extractor obeys them on tricky multi-source inputs. A lightweight Git equivalent does not need an automated judge service: a small held-out set of realistic source pairs with explicit pass/fail behavioral oracles, plus occasional checks asking a fresh coding or SRE agent to answer a hard task using only `docs/knowledge/`, tests the actual consumer outcome without changing the Markdown store.

### 2. Protecting curated edits across re-extraction

Knowledge Catalog explicitly protects certified Query Templates from being modified or deleted by later enrichment runs. In [knowledge.md](../../extract-session-details/references/knowledge.md), a subject rebuild preserves `owner instruction` rows in History, and re-extraction keeps holders and relation lines. If teams manually refine a high-value rule explanation or verified worked example on a subject page and later re-run extraction after upgrading a skill, there is no explicit marker telling the extractor to preserve that human-verified block untouched.

### 3. Keeping Git review disciplined

Treating `git commit` as the approval gate works cleanly for a solo owner or small team only if extraction runs leave edits uncommitted or on a review branch. If an autonomous agent commits Stage 3 updates straight to `main` alongside code changes, the review boundary disappears. Writing that expectation into project workflows, or reviewing `docs/knowledge/` diffs separately from source-transcript commits, keeps the Git gate real without inventing a proposal database.

### 4. Scaling beyond flat navigation

In a single-project store, `docs/knowledge/index.md`, `subjects.md`, and canonical procedure links give a consuming agent progressive disclosure. If one store grows to cover many teams or loosely related services, a flat registry can expose competing terminology and blow past prompt budgets. Knowledge Catalog handles that with bounded context sets per domain. Under `ok-skills`'s extraction-only scope, leaving retrieval and packaging out is deliberate, but collaborators should check whether their target repository stays within one coherent domain or needs per-domain folders or indexes later.

## 6. What ok-skills deliberately leaves out

Several major features of Knowledge Catalog belong to cloud infrastructure or runtime serving and do not need to be replicated here:

- **Automatic schema and data-lineage discovery** across cloud data warehouses.
- **Managed console workflows and chained change-request batches** for hundreds of cloud assets.
- **Uncalibrated numeric confidence gates** such as auto-publishing at 0.85 confidence.
- **Runtime serving endpoints** such as MCP lookup servers, character-budget packers, and IAM-filtered retrieval APIs.

## 7. Questions to review with collaborators

When sharing this repository and deciding what to tighten next, five questions focus the review:

1. **Downstream evaluation:** What small set of held-out source fixtures and consumer questions should live in this repository, or in each target project, to prove that `docs/knowledge/` prevents real mistakes for coding, SRE, and assistant agents?
2. **Validating the newest rules:** Have real or synthetic multi-source runs shown that the scope-compatibility and rule-application instructions in [knowledge.md](../../extract-session-details/references/knowledge.md) and [store.md](../../extract-session-details/references/store.md) stop homonym collisions without flooding `docs/knowledge/unassigned.md`?
3. **Review discipline:** Is reviewing `git diff` before committing sufficient for everyone using these skills, or do multi-contributor repositories need branch and pull-request rules for `docs/knowledge/`?
4. **Curated overrides:** If teams re-run extraction after upgrading these skills, do manually verified notes or worked examples need an explicit preservation marker like Knowledge Catalog's certified Query Templates?
5. **Context boundaries at scale:** When a repository holds many services or domains, is one `docs/knowledge/` tree with `subjects.md` enough, or should teams partition stores by domain boundary?
